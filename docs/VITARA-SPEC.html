01

What this is

Vitara is the health module of Maaya OS, a self-hosted personal system running on one Mac mini. It does two jobs that used to be one, and are now deliberately separate processes:

ProcessJobPort
vitaraIngestion. Pulls from Oura, accepts Apple Health imports and manual entry, serves raw readings.5100
vitara-workerThe sync loops that fetch from Oura and MyFitnessPal.—
vitara-insightAnalysis. Baselines, statistics, findings, correlations.5110

The business question it answers

A ring reports last night's numbers. That is not useful on its own, because "HRV 38ms" means nothing without knowing what your HRV usually is. A population reference is worse than useless here — an athlete's normal and a sedentary person's normal differ by more than any illness would move either.

So the system answers three questions the device cannot:

  1. What is normal for this person? — baselines, per metric, over sixty days, excluding periods that should not count.
  2. Is anything off it right now? — findings, computed in code, deduplicated and rate-limited before they reach the user.
  3. What moves with what? — correlations between what the person does and how they recover.
The architectural rule

No language model touches any of this. Everything from raw reading to finding is deterministic arithmetic. The model is shown findings afterwards and asked what is worth saying; it is never asked what happened.

That is why identity keys for findings are derived from content in code. A model asked to generate a key produces a different one every run for the same condition, and then nothing can be deduplicated, cooled down, or resolved — the same elevated heart rate would arrive as a fresh alert every morning.

02

The pipeline

Why one database, split by ownership

The alternative — a second store for the analysis — buys process separation at the price of a sync problem and two versions of the truth. The analysis needs every raw observation, so copying health data across a process boundary would mean keeping two copies in step forever.

Instead the write sets are disjoint. SQLite in WAL mode serialises the writes it must, and no two processes ever contend for the same row. Only vitara creates schema: two processes racing to CREATE TABLE IF NOT EXISTS on a cold boot is how the database ends up locked.

They share an environment file too, vitara.env, so any setting that must differ per process — the port above all — has to be overridden under that service's environment: in docker-compose.yml. Missing exactly that shipped Insight listening on the wrong port.

Two things worth knowing about the sync

The sleep score lives on a different endpoint from the sleep. Oura's sleep endpoint returns the session detail; the 0–100 score comes from daily_sleep. They are fetched separately and merged.

The watermark is per-collection. An earlier version tracked one "latest day" across sleep, readiness and activity only — so if SpO2 failed for a fortnight while sleep kept succeeding, the next window started from sleep's date and those SpO2 days were never fetched again. GetLatestDaysAsync() now returns one watermark per collection.

The nap trap

Oura's sleep endpoint returns every sleep period it detects — naps, "rest" periods, and sensor noise — and the record carries no type field to tell them apart. In the real database, single days held several sessions of only a few minutes alongside the actual night, and some held a zero-minute session beside it.

Projecting each session separately counted every one of those as a night. Each contributed a full night's deficit against a ~7-hour need, and the system reported 51 hours of sleep debt. Worse and quieter: the total_sleep_minutes baseline pooled 5-minute values with 400-minute ones, so its mean collapsed and its spread exploded, making every sleep z-score meaningless. The projector now aggregates per day — see §07.

04

The other sources

Apple Health — spreadsheet

For CSV, TSV and XLSX files produced by third-party export apps. Detects two layouts automatically: wide (one row per day, one column per metric) and long (one row per sample). Header text is normalised rather than enumerated, so Resting Heart Rate, resting_heart_rate and HKQuantityTypeIdentifierRestingHeartRate all resolve to one key.

Apple Health — the native export

Apple's own export.xml. A real one measured 810MB with 1,788,396 records from nineteen apps spanning 2016 to 2026. Parsed with XmlReader in 6.7 seconds using 46MB of RAM — nothing accumulates except one number per (day, metric, app).

Uploaded once and parsed once. The obvious preview-then-commit shape would send 810MB over the network twice, so the upload parses straight to daily aggregates and stages those under a token; the commit works from them.

Four traps in a real Apple export

Oura writes into Apple Health. It was the largest single writer at 714,384 records. Since Oura also reaches Vitara through its own API — with sleep stages, RMSSD and a temperature deviation Apple never receives — importing it would overwrite the better record with a coarser copy of itself. The importer lists every source with its real counts and leaves Oura unticked, because which copy to keep is a decision, not a rule.

Units are imperial. lb, in, mi, degF throughout. A body mass of 176 stored as kilograms is a number that looks entirely reasonable.

SDNN is not RMSSD. Apple records heart-rate variability as SDNN; Oura records RMSSD. They are different statistics over the same intervals. Apple's gets its own metric key, hrv_sdnn, and never touches the field holding Oura's.

Sleep is spans, not values. A SleepAnalysis record carries no number — it is a start, an end and a stage name. A night is the summed duration of the asleep spans (never "InBed"), filed under the day the person woke.

Plausibility bounds

Found only by running the real file. It contained a "resting heart rate" far above any possible resting value, a night of well under a minute, another over fifteen hours, and days with a single step — the nap trap's whole family at ten-year scale. Values are bounded after daily aggregation, and anything dropped is counted and reported.

Context signatures — the important design decision

Baselines are computed per (metric, context signature). The obvious reading is to key on every context field, and that is unusable arithmetic:

Why not every field

Blood pressure keyed on position, arm, fasting, time of day, caffeine and alcohol is dozens of signatures, each needing ~30 readings before it says anything. Nobody accumulates thirty morning-seated-left-arm-no-caffeine-no-alcohol-fasted readings. Every bucket stays permanently invalid and the feature silently never works.

So each metric declares only the context that genuinely changes the number:

Every other context field — arm, cuff size, caffeine, alcohol, pre/post exercise — is still recorded on the observation. It is there to explain an outlier six months later; it just does not fragment the baseline.

07

Projection

ObservationProjector turns typed rows into flat observations. It is pure and synchronous — no database, no clock — so the same rows always produce the same observations, which is what makes re-running a backfill safe.

Rules

  • One row per day per metric. Oura returns naps and noise alongside the night; each session projected separately is the 51-hour bug.
  • Additive fields sum — total, deep and REM sleep minutes.
  • Point-in-time fields come from the longest session — score, HRV, breathing rate, SpO₂, skin temperature. A five-minute mis-detection's HRV is not the night's HRV, and averaging them corrupts a real reading with a fake one.
  • Missing readings are omitted, never written as zero. A missing HRV is not an HRV of zero, and a baseline that averages in the nights the ring was not worn describes someone else.
  • Oura's day field is used as-is, never re-derived from a UTC instant — that is how sleep starting at 11pm ends up filed under tomorrow.
  • The observation instant comes from the main session, so the unique index stays stable. A moving instant would leave the old row beside the new one and double-count the day.

The projection window is 120 days by default (VITARA_PROJECT_WINDOW_DAYS), wide because Oura revises recent days and a backfill can land months at once. Re-projecting is free — the upsert ignores rows that already exist.

08

Baselines

A baseline is what "normal" means for one metric, for this person, right now. It is computed over a rolling 60-day window and requires at least 21 readings to be marked valid.

Why exclusions are the point

A mean is not enough. Two weeks of illness inside a rolling window raises the baseline — and the system then stops flagging exactly what it exists to flag, while every number it reports still looks perfectly reasonable.

What is excluded

  1. Excluded periods — illness, injury, anything the user marked. Dropped entirely.
  2. Travel, for circadian metrics only. Cross-timezone travel corrupts sleep timing rather than merely influencing it: sleep in a different timezone is not a worse night, it is a different question, and pooling the two produces a baseline describing neither. The circadian set is total_sleep_minutes, deep_sleep_minutes, rem_sleep_minutes, sleep_score, sleep_efficiency, hrv_rmssd, resting_hr, readiness_score. Steps and weight are unaffected by which timezone you are in, so they stay.
  3. Statistical outliers, by median absolute deviation — see §09.

Everything dropped is recorded in ExclusionsJson, so a baseline can explain itself when someone asks why a number looks different from what they expected.

Validity

Below 21 readings the baseline is marked IsValid = false and exposed rather than hidden. "Not enough data yet" is a real answer; silently omitting the metric looks identical to the metric not existing. No z-score is ever computed against an invalid baseline — a confident number built on four readings is the one that gets acted on.

Sleep need: where the spec was wrong

The circularity

The spec said to derive habitual sleep need "from their long-run distribution, not a fixed 8 hours". That sounds right and is not.

If someone is chronically short, taking the centre of what they actually sleep computes their deficit as their requirement — and then reports, forever, that they are not in debt. The system would be most confident exactly when it was most wrong.

There is no way to recover sleep need from sleep duration. What is available:

  1. Let the user say. VITARA_SLEEP_NEED_MINUTES. The only input here that is a fact rather than an inference.
  2. Failing that, the upper quartile of the last 90 nights — the longest quarter are the nights closest to unconstrained (weekends, no alarm), so p75 is a floor on need rather than a description of habit. Clamped to 7–9.5 hours. Below 30 nights it falls back to 8 hours and says so.

The basis travels with the number wherever it goes. "You are four hours short" means something different when the need behind it was inferred rather than stated.

Debt accumulation

for each night, oldest first:
    delta = need − actual
    if delta > 0:  debt += delta              a short night adds fully
    else:          debt += delta × 0.5        a long night pays back at half
    debt = max(0, debt)                       debt never goes negative

Surplus repays at half rate because an extra hour on Saturday does not undo an hour lost on each of five weeknights. Debt is floored at zero because banking sleep is not a thing, and a negative running total would silently offset a future genuine deficit.

The rules that keep it quiet

Sustained is the cheapest and most effective noise filter available. A single odd night is a single odd night, and a system that says so every time is one that gets muted. Deviation requires the breach on consecutive days in the same direction — a metric bouncing above and below is unsettled, not deviating, and calling that a finding describes the noise rather than the person.

Deviation fires for ten curated metrics, not everything with a baseline. Two sigma sustained over two days is roughly one day in a thousand per metric, which sounds negligible until it is multiplied by thirty metrics and 365 days. Worse, these metrics are heavily correlated — deep, REM and total sleep move together, so one poor week arrives as four findings saying the same thing. The list: resting HR, HRV, skin temperature, total sleep, readiness, breathing rate, SpO₂, systolic BP, weight, glucose.

The illness detector suppresses its own components. "Resting HR is high, HRV is low, temperature is up, and you may be getting ill" is four notifications about one thing.

Why two of three, and why it matters most

The illness detector is the most valuable thing here and the one most able to destroy trust in everything around it: fire it spuriously twice and it stops being read, including on the morning it is right.

Each day must independently show at least two of the three signals. Not one of three — any single one moves for a late meal, a hard session, a warm room. And not "resting HR up on Tuesday, HRV down on Thursday", which is two unrelated days rather than a signal.

Staleness applies to the dense tier only. A weight entered by hand every few days, or a lab drawn twice a year, is not missing — it is scheduled. And a metric never recorded is not stale either; that would be the system complaining about its own emptiness on day one.

Missing data is a finding, not a gap to paper over. A ring left in a drawer produces exactly the same silence as a week of perfect health, and only one of those is worth saying nothing about.

Regime change, and why the dwell is load-bearing

A sustained step change is not a deviation to be averaged away — it is a new normal. A rolling baseline that absorbs it over sixty days ends up describing neither the old level nor the new one, while never mentioning that anything happened.

The failure mode without a dwell requirement

Without requiring the new level to persist, a twitchy detector resets on every wobble. Once "normal" is redefined every few days, nothing is ever abnormal again — the detector quietly disables the entire system it feeds, and it looks like it is working the whole time.

Two bugs found while building it: it fired on pure noise, because MAD goes to zero on a steady metric and any step then looks infinite; then it could not detect anything on zero-variance data. Fixed with a pooled MAD across both windows, an explicit distribution-separation test, and degenerate-case handling.

Severity runs the opposite way to what you might expect: a step with no candidate explanation is notable, one with an explanation is only info. A resting heart rate that stepped up the week a new ring arrived is probably the ring. One that stepped up for no visible reason is the one worth a look.

Attribution is attempted and phrased as a possible explanation, never a cause. A device change on the day a metric steps is worth knowing; asserting it did it is a claim the data cannot support.

11

Correlations

Looking for relationships between what the person does and how they recover. Does a hard session cost HRV tomorrow? Does a short night raise resting heart rate?

The hard part is not the correlation, it is not lying about it

Thirty metrics is 435 pairs before lags. At p < 0.05 that is twenty-two "findings" per run from pure noise. Three confident wrong statements a week is how a feature stops being read.

Four decisions carry the honesty here, and removing any one breaks it:

  1. A curated pair list. Four drivers (active calories, steps, total sleep, high-stress seconds) against six outcomes (HRV, resting HR, readiness, sleep score, total sleep, skin temperature). Pairs where a mechanism is at least plausible — which also means a result has something to be checked against.
  2. Lagged one direction only. Today's training can affect tomorrow's HRV; tomorrow's HRV cannot affect today's training. Lags of 0 and 1 day only — further out means more tests and a weaker mechanism, and a seven-day lag on daily data is mostly a test of whether the week was busy.
  3. Benjamini–Hochberg FDR control at 0.10, across the whole run. Even sixty tests at p < 0.05 expect three spurious hits every time. BH controls the expected proportion of false discoveries rather than the chance of any — the right trade here, where missing a real relationship costs far less than asserting one that is not there. Applied across the run, so adding a pair raises the bar for every other pair rather than quietly lowering it.
  4. An effect-size floor of |ρ| ≥ 0.3. Over enough days almost anything reaches significance. A significant 0.12 explains one percent of the variance and is not worth a sentence.

Minimum 30 paired days before a pair is tested at all. Below that the confidence interval on a correlation is so wide that a reported 0.4 is compatible with zero — and a number with that much uncertainty, shown without it, gets acted on as though it were solid.

The caveat that these are not causes is returned by the API rather than written into the UI, so every surface showing the numbers carries identical words.

12

Finding lifecycle

SyncFindingsAsync is a reconcile, not an insert. Each pass compares what was detected against what is already open.

OutcomeConditionEffect
OpenedKey matches nothing openNew row inserted
ContinuedKey matches an open findingSeverity, summary and evidence updated. FirstDetectedLocal is left alone.
ResolvedOpen, but not detected this passResolvedLocal set. Never deleted.

Keeping the original detection date is what lets a finding be reported as "day 5" rather than as something new every morning — the difference between a system tracking a condition and one repeating itself.

Resolution is recorded rather than deleted because the condition ending is information too. "Your resting heart rate is back to normal" is worth as much as the original finding, and a deleted row can never say it. An empty detection set is meaningful: it means everything open has resolved.

How findings reach the user

HealthFindingsWorker in San polls every 3 hours and hands findings to San's existing FindingDispatcher — the same path email triage and system audits use. That gives keyed deduplication, cooldowns that lengthen when something is ignored, and a separation between "message the user" and "tell NorthStar". A second notification path would mean a second cooldown to tune and a second place for the same finding to arrive twice.

Nothing maps to critical. A system inferring from a ring is not equipped to declare an emergency; the most it should do is say something is worth a look.

13

Every threshold

All environment-overridable, set in deploy/env/vitara.env. The spec left every one of these unspecified, and they are the difference between a useful system and one that is muted within a fortnight.

Why they are tunable at all

This project has already watched a notification channel become something to ignore. The lesson was not "send fewer" — it was that a detector nobody can tune eventually gets muted wholesale, taking the true positives with it.

The status sentence

/api/health/summary leads with a plain-English status field, not just dates. Asked "is anything wrong with my health", San once answered "nothing is flagged as being outside your normal range" — from an empty findings list, on a box where the analysis had never run. Zero findings and no analysis are the same JSON shape, and the model read the reassuring one.

computedThrough and daysBehind were both in the payload and it went straight past them. A number a model may or may not interpret is not a safeguard; a sentence that says "this has never been computed, do not tell the user they are fine" is.

Why it is not a nightly job

The spec called for a midnight run. That is wrong for how this is used: the user syncs Oura in the morning, so at midnight the night that just finished has not arrived yet. A job running then computes on absence, writes a baseline missing its most recent day, and reports staleness for data that is merely not downloaded.

So it is driven by the data, not the clock. It wakes hourly, compares the newest observation against the newest baseline, and does nothing unless there is something new. Correct whenever the sync happens, and self-healing when the sync is late or fails.

The staggered first-run delays are deliberate: every worker hitting the modules in the same second after a restart is a self-inflicted thundering herd.

Failures that shaped this

Every one of these is in the code as a comment next to the thing it caused. They are collected here because the reasoning is not obvious from the result.

What happenedWhat changed
51 hours of sleep debt. Oura naps counted as nights — several few-minute sessions alongside the real one on a single day. Projector aggregates per day. Additive fields sum, point-in-time fields come from the longest session.
"Nothing is flagged as outside your normal range" — from an empty table, on a box where the analysis had never run. status sentence in the summary payload, said in words a model cannot skip.
Regime detector fired on pure noise, then could not detect anything on zero-variance data. Pooled MAD, separation test, explicit degenerate-case handling.
SpO2 stopped syncing for a fortnight and was never re-fetched, because one watermark covered all collections. Per-collection watermarks.
Date range filters silently dropped rows. Day was stored via ToString() in a culture short-date format; SQLite compares TEXT lexicographically. Normalised to yyyy-MM-dd at startup, idempotently.
The dashboard showed four-day-old vitals as today's. daysAgo on every metric block, and in every summary San reads.
An Apple export contained a "resting heart rate" far above any possible resting value and a night of well under a minute. Plausibility bounds after aggregation, with every drop counted and reported.
nginx would have rejected the 810MB upload with a 413 at a 100m site-wide cap. Dedicated location block, 2g limit, request buffering off, 30-minute timeouts.
The Insight tab returned 502 from the day it shipped. vitara-insight shares vitara.env with vitara, which sets BIND_URL to 5100 — so Insight listened on 5100 while nginx, San and the MCP gateway all called 5110. The findings worker silently read nothing. A service-level environment: BIND_URL in docker-compose.yml, which wins over env_file: one shared secrets file, one port per process.
17

Restraint and proof

A review of this spec by another model raised five things. Four are now in the code and are described here so they stop reading as open questions; the fifth is in what is not built. All four are about the same underlying risk: a system that detects correctly, says too much, and is muted inside a fortnight.

At most three findings lead

Detection and surfacing are separate jobs. Every active finding stays active and stays in /api/health/findings; Surfacing decides only which few lead today. Severity first, then newest first at equal severity — a finding on its fortieth day has been said thirty-nine times, and duration is what makes a finding certain, not what makes it news. Anything high always leads, past the cap if necessary, since a cap that hides a serious finding does the opposite of its job on the morning it matters. The rest are returned under standing with a count, so a caller can never shorten the list silently.

Cap: VITARA_SURFACED_MAX, default 3.

What has no normal yet is said out loud

"Nothing is outside your normal range" is true and misleading when half the metrics have no normal to be outside of — four readings and ninety readings look identical once they are inside range. /api/health/summary now carries a coverage block: how many measurements have earned a baseline, how many are still learning, which ones, and an instruction to say "not enough data yet" rather than implying those are fine.

Skin temperature is bracketed in degrees

The ring reports a deviation from its own long-run reference, and Vitara baselines that deviation again. That is deliberate: it cancels a standing offset, so someone who always sleeps a fifth of a degree warm is not called feverish every night. But a z-score of a deviation fails in two silent ways. A tight distribution makes noise significant — five hundredths of a degree, inside the sensor's resolution, clears 1.5 SD. A drifting reference does the reverse: if the ring's baseline creeps up with the user, the reported deviation stays near zero while the person genuinely warms.

So the z-score is bracketed. Below VITARA_ILLNESS_TEMP_FLOOR_C (0.15 °C) an unusual reading does not count at all; at or above VITARA_ILLNESS_TEMP_OVERRIDE_C (0.50 °C) it counts whatever the z-score says. Applied in the illness detector and to the standalone deviation finding, or the wobble rejected by one arrives through the other. The floor guards the warm side only — running colder than usual is a real reading and is still reported.

The illness detector is scored against the days you were ill

The one detector here with ground truth available. Illness periods are already marked so they stay out of baselines; those marks are the labels. /api/health/illness-eval replays the shipped detector — not a copy of its rule — day by day, groups the days it would have spoken into runs, and reports three numbers:

MeasureWhat it means
caughtAn illness with a signal running into it or through it. A signal more than 7 days early is not credited, or any noisy detector looks prescient.
leadDays between the signal starting and the illness being marked. Positive is a warning; zero or negative is confirmation, reported separately because averaging the two hides which one this detector gives.
false alarmsRuns of signal with no illness near them. The number that decides whether the detector survives a real user. A signal still running two days past the marked end is the same episode, not a new alarm.

The verdict is a sentence and is deliberately unflattering: two episodes produces "too few to conclude anything, treat this as an anecdote" rather than a percentage that reads like a result. It is shown in the Insight tab, because a detector that has never caught anything should say so where the reader can see it.

The forecast has to beat the dull answer

The bio signature has two halves. Signature is the portrait — when this person sleeps (bedtimes averaged around midnight, or someone who sleeps at 23:00 and 01:00 lands at noon), how far free nights drift from working ones, which weekday is weakest, how long a hard day costs, what their own data responds to. Each part refuses to speak without enough behind it.

Prediction is the half that can be wrong in public: tomorrow's readiness and resting heart rate, from seven legible features, ridge-fitted on this person alone. It is scored by rolling origin — fitted only on days before the one being predicted — against two rivals: assuming tomorrow is like today, and assuming an average day. "Tomorrow is like today" is a genuinely strong forecast for physiology, and a model that cannot beat it by a real margin is the same answer dressed up as insight. When it loses, the naive answer ships, labelled. Losing is not an error state and is not hidden.

/api/health/signature, /api/health/forecast. Computed on demand; no table, no migration.

Lab reference rangesLabPanels and ReferenceRanges exist, lab_anchor is a defined finding type, nothing populates or reads them. Lab values can be entered manually; they are stored but not interpreted.

Decided: labelled, not dropped

/api/bioage reports a biological age that is not PhenoAge or any validated model — it is a weighted average of Oura's own HRV, resting HR, sleep and readiness scores with hand-picked weights, and under the evidence scale this system otherwise uses it would grade D or lower.

It was labelled rather than removed. The payload now carries its own label, method and disclaimer, and a per-factor contributions breakdown in years that sums to the reported delta — so the number cannot be shown without the sentence saying what it is, and a reader can see exactly which measurement moved it. PhenoAge remains the thing to replace it with; it needs nine lab markers that are not ingested.
